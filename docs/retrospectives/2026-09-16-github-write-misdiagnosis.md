# GitHub写入误判复盘

整理日期：2026-09-16。范围：laojia-a/home历史归档过程中，“此前能写，现在不能写”的判断及其纠正。依据为可见对话和本轮回读的GitHub对象；没有平台内部日志，不推断后台发生了什么。

## 1. 结论

问题不是已经证实GitHub连接器不可写，而是助手没有完成必要的能力发现和实际验证，就把局部失败扩大成了整体不能执行，并用长篇解释替代继续排查。

用户要求把历史成果保存在GitHub。助手多次建议下载、换工作区，把自己尚未完成的交付转给用户；随后同一对话通过连接器成功创建分支、提交真实SVG并回读。这直接推翻了“当前对话不能写GitHub”的笼统结论。

正确经验不是“GitHub永远能写”，而是：**可用与不可用都按当前具体动作的证据判断，不用猜测代替验证。**

## 3. 判断错在哪里

**把执行路径混在一起。** 命令行git、浏览器和授权GitHub连接器不是一次调用。CLI域名解析失败只能先定位到CLI这次请求，不能跨路径外推。

**把工具发现结果当作平台能力结论。** 只查看当前已载入动作，或某个过滤关键词没有结果，不足以认定整个连接器没有写能力。尤其在对话中已有成功提交证据时，应该先查具体动作，再判断。重新发现有结果也只说明动作可以尝试，真正完成仍以调用和回读为准。

**把“尚未验证”说成“确定不能”。** 没有掌握后台原因，却给出工具变化、只能换到其他工作区等解释，增加了用户不必要的操作。此次能确认的是排查和表述错误，不能确认后台是否发生过能力变化。

**把局部操作与最终交付混算。** blob创建、分支指向、文件提交、main合并和全量归档是不同结果；传过片段、写过workflow、生成过本地ZIP，都不能直接写为全量入库。

**让失败方法反复拖住工作。** 历史中已有长段压缩切片损坏的记录。连接器能写小文本，不代表在对话中转写大量编码数据适合整包传输。应该缩小批次、做独立校验、及时形成可读提交；发现损坏先定位，不继续追加未知完整性的流。

**过早把工作交回用户。** 在授权路径未穷尽、尚无确证阻断时，要求用户下载并转交另一个工作区，改变了用户原本要求的完成方式。

## 4. 对执行的影响

用户反复追问“是否真的入库”“连接是否有问题”，归档进度和能力解释相互混杂。接手者可能误认为需要重新授权、重新导入全部源码或换环境；这部分额外成本来自助手判断失准，而不是已证明的仓库问题。

用户指出过去成功后，正确动作应当是立刻复核和缩小问题范围，不是坚持维护上一条解释。新的实测一旦推翻旧结论，应直接更正并继续完成授权任务。

## 5. 改正措施

将可复用教训写入[LESSONS](../../knowledge/LESSONS.md)，将小型UTF-8文件已验证路径写入[PLAYBOOK](../../knowledge/PLAYBOOK.md)；AGENTS仅增加短规则和入口。不要再把全部复盘塞进AGENTS，也不把一次事件升格为通用平台保证。

今后声称“不能写”必须说明具体仓库、动作、路径、实际错误以及还没有验证的部分；声称“已经写入”必须有提交、分支和文件回读。遇到超时先检查是否已经成功，遇到版本冲突先比较，遇到明确授权拒绝停止而非绕过。

## 6. 本次经验的边界

这次验证范围是同一仓库的小型UTF-8原始SVG。全量历史包、二进制文件、大批量上传、保护分支写入和未来工具可用性都不由此自动成立。

本次复盘不重写页面、不重复导入生产源码、不把归档任务勾成完成。它修正的是能力判断和交付报告方法；剩余实物归档仍需实际写入与逐项核验。
